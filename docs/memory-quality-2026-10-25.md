# 真实模型召回、记忆生成与性能复核 — 2026-10-25

本次验证不能得出“全部达到 v1 目标”的结论。原生小样本召回通过既定 smoke 阈值，真实服务在低并发下可用；复杂外部长对话召回、模型提取稳定性及高并发延迟仍有明确不足。CI 正确性通过与模型质量达标是两件需要分别验证的事。

聚合数据见 [JSON](memory-quality-2026-10-25.json)。原始结果、逐查询分解、失败记录、模型响应和外部数据只保存在忽略的 `.artifacts/quality-20261025/` 中，不分发原始外部数据或凭据。

## 配置与验收口径

- 本机 Apple M5 Max，18 核 CPU、64 GiB 内存，macOS 27.0.1 arm64；PostgreSQL 16.14 + pgvector，Redis，服务使用隔离数据库和独立端口。没有重置原有测试服务的数据。
- Embedding 是本地 Ollama `qwen3-embedding:4b-q8_0`，2,560 维；实际 digest 记录于 JSON。文本生成使用用户配置的 `deepseek-v4.1-flash:1017-cloud`，经 Ollama 调用云端，不能称为本地文本推理。
- 原生数据既有目标：Recall@3 ≥ 0.70、MRR ≥ 0.65、nDCG@5 ≥ 0.67，wrong-user / negative / stale-fact-top-3 均为 0。没有把这个小数据集的阈值事后套到外部数据集。
- 服务既有目标：检索 P95 < 250ms，Summary P95 < 60s，Analysis P95 < 120s。运行规模、到达方式和失败覆盖率必须一起看；成功阶段的 P95 不能掩盖未完成任务。
- 检索主执行器使用生产 `MemoryEngine`，四种排序 ablation 保留。外部质量轨道使用内存 repository/vector adapter 和真实 Qwen 向量，避免把其耗时当作持久化服务延迟；另用真实 PostgreSQL / HTTP 轨道测性能。
- 严格 provider 评测遇到 embedding 失败直接失败，不把线上可能发生的 lexical fallback 计作模型质量。在线 HTTP 轨道没有逐请求 fallback 标识，本次服务端和 Ollama 保持可用，但不声称每个请求都有独立 embedding trace。

## 召回结果

以下是 `full` 变体；Recall 是命中相关证据的比例，不能与最终回答准确率混用。

| 数据与规模 | Recall@3 | Recall@10 | MRR | nDCG@5 | 判断 |
| --- | ---: | ---: | ---: | ---: | --- |
| 原生 77 文档、24 查询 | 95.83% | 见下述限制 | 1.0000 | 0.9753 | 通过既有 smoke 阈值 |
| LOCOMO 10 个对话、5,882 个原始轮次、1,532 查询 | 55.27% | 70.96% | 0.5458 | 0.5299 | 复杂召回存在明显遗漏 |
| LongMemEval cleaned V1，12 查询、585 session | 92.50% | 100% | 1.0000 | 0.9831 | 分层小样本，不能外推至全量 |

原生查询自己的 TopN 优先于 CLI 默认值，常为 3，因此它导出的 Recall@10 不是“每次返回十条”的实验。原生 full 的 wrong-user、negative、stale-top-3 均为 0；semantic-only 的 stale-top-3 为 1.39%，full 的时间/状态处理改善了这一点。full 与 full-no-relations 相同，未观察到额外图扩展收益。

LOCOMO 只索引原始对话，不索引人工事件摘要或上游生成的观察。按上游 sample_id 的 SHA256 排序，预先选择 `conv-47` / `conv-48` 为 holdout，其余八个为 development，未按得分挑样本。Development 1,191 查询 R@3 55.05%，holdout 341 查询 56.03%。按十个对话进行 3,000 次 cluster bootstrap（seed 20261025），整体 R@3 的描述性 95% 区间约为 52.39%–58.50%；对话簇很少，不应作精确的总体保证。

LOCOMO 分类 1 / 2 / 3 / 4 的 R@3 分别为 31.44% / 63.85% / 35.49% / 62.09%，其中分类 1 和 3 最弱。这是证据轮次检索分数，不是官方端到端 QA 或榜单分数；跳过没有正向检索证据的分类 5。该轨道没有真实关系边、importance 一致，四种排序变体相同是预期现象，不能据此判断图能力在真实生成记忆上无效。没有 stale/negative 标注的外部数据中，这两项为 0 也不构成安全证明。

LongMemEval 在 500 条 cleaned V1 查询中，按六类 question_type 分层，各选 SHA256(question_id) 最小的两条：一条 development、一条 holdout，选择时不读答案。Development / holdout 各六条的 R@3 为 91.67% / 93.33%；精确 ID 和选择方法在 JSON 中。它不是 500 条全量结果，不是 V2，也没有执行官方 QA judge；较长 session 命中容易，不能与 LOCOMO 轮次粒度直接横比。

## 从来源到回答的真实回放

新建八组虚构用户场景、27 个问题，覆盖否定、助手建议、跨会话修正、相似实体、说话人归属、假设、日期更新、任务完成、中英文和跨用户 canary。通过真实 Gateway 结束会话、outbox、Worker、持久化存储、HTTP 召回和注入，不向线上用户写入测试内容。每组问题在所有用户完成材料摄入后才运行；临时 API Key 在运行结束时撤销。

每个问题比较默认注入、仅派生记忆正文、无记忆。默认注入可包含保留的原始片段；仅派生模式排除原始片段、证据引文和来源元数据，避免把原文效果归功于模型生成记忆。答案只接受预期字符串、布尔值或明确 null，不使用同一个模型给自己打语义分。生成和回答仍使用同一模型，因此这是闭集功能诊断，不能作为独立 judge 或泛化质量证明。

| 运行与变更 | 完成问题 | 正确数 / 全部预期问题 | 主要失败 |
| --- | ---: | ---: | --- |
| 初始实现 | 24/27 | 24/27 | 任务条目缺字段 / 分数不合法 |
| 补全 item schema | 21/27 | 21/27 | `supersedes` 数组被输出成字符串 |
| 最多一次 LLM schema 纠正 | 24/27 | 24/27 | 替代引用的 key/subject 与旧事实不一致 |
| 提示词明确精确复用旧 key/subject | 27/27 | 27/27 | 本轮默认注入无错；仅派生记忆仍有一题未答 |

最终完整运行覆盖率 27/27，默认注入正确 27/27，仅派生记忆 26/27，无记忆 3/27；24 个已知问题和三个无答案问题在默认注入中均正确，HTTP 结果跨用户命中为 0。派生模式唯一未答的是虚构取件暗号：模型把它视为凭据而没有写入派生正文，默认注入从保留的原始片段回答。这里涉及记忆保留策略，不能简单把它当作向量召回错误，也不能削弱凭据保护去追求满分。成功阶段 Summary / Analysis P95 为 19.9s / 64.9s，检索 P95 177.6ms，本轮在此小样本中满足相应延迟目标。

上面各轮失败都保留，不挑成功的题计算准确率。前几轮对完成的问题都回答正确，也不能把未完成的题排除后宣称 100%。最终一轮通过尚不能证明多次运行稳定性或复杂长会话质量。schema 纠正只允许模型从原始来源重生成，不进行字段强制转换；引用与语义校验继续拒绝不合法输出。

初始运行检索 P95 377.3ms、成功 Summary P95 25.1s、成功 Analysis P95 194.2s，已暴露超时和重试影响。格式纠正轮成功阶段的 Summary / Analysis P95 降为 20.2s / 28.0s，但仍有一个会话等待超过五分钟，不能据成功阶段延迟宣称整个异步链路达标。此工具等待 summary/analysis 状态，不单独等待所有 Key Memory、来源评分或 embedding 扇出任务完成；完整节点覆盖率和所有后台阶段的 SLA 仍需扩展验证。

## 真实持久化服务负载

通过生产 store 接口向专用测试用户写入 10,000 个 entity 及其真实 2,560 维向量。它们重复 77 段合成文本并复用相应模型向量，是容量 fixture，不能当作一万条独立准确率样本。辅助时间图节点不计入实体向量覆盖；10,000 个实体向量均已就绪。

经 API Key 鉴权访问 HTTP memory/search，每次 top-5。重复查询与追加唯一 nonce 的查询分开测，预热不计入测量；“唯一”用于避免相同查询命中缓存，并不等于不同任务质量样本。测量不含客户端等待并发槽位的时间。

| 到达方式 | 查询方式 | 并发上限 / 实测峰值 | 每阶段请求数 | P95 |
| --- | --- | --- | ---: | ---: |
| 12 offered RPS，有并发上限 | 重复 | 上限 1 / 4 / 8，旧报告未记录峰值 | 100 | 159.6 / 149.5 / 158.2ms |
| 12 offered RPS，有并发上限 | 唯一 | 上限 1 / 4 / 8，旧报告未记录峰值 | 100 | 174.0 / 169.1 / 171.7ms |
| 无 pacing、闭环请求 | 重复 | 峰值确认为 1 / 4 / 8 | 32 | 149.2 / 230.0 / 590.3ms |
| 无 pacing、闭环请求 | 唯一 | 峰值确认为 1 / 4 / 8 | 32 | 168.7 / 308.7 / 660.4ms |

两组分别共 600 / 192 请求，错误、空结果、跨用户返回均为 0。前一组在低到达率下满足延迟目标，不能称作八路持续并发达标；后一组在四路唯一查询和八路并发时明确超过 250ms。闭环样本较少，是故障定位信号，不是长期稳态容量上限；设置 250ms 阈值的命令保留报告并返回失败，没有放宽阈值使其变绿。

独立诊断：直接调用 Ollama embedding，不经 MemStation / SQL，32 请求的 1 / 4 / 8 并发 P95 为 49.9 / 165.0 / 327.0ms。八路时仅 embedding 队列已超过检索总预算；同时实际 SQL 的 EXPLAIN 样本约 38.6ms，2,560 维当前使用精确距离扫描与排序，没有 ANN 索引。因此不能把全部 HTTP 延迟归咎于数据库，也不能只加索引就承诺达标。未在本次仓促新增高维 ANN 迁移。

本批另补充阻塞的 Manager production build，Go 全量（独立 PostgreSQL 集成库）、相关 race、format 和 lint 已在本地通过。本批新增评测和 LLM 修复的完整远端结果以其对应提交的 [CI](https://github.com/backrunner/memstation/actions/workflows/ci.yml) 为准，不能用前一个 UI 提交的通过替代。默认 CI 继续阻塞真实正确性门禁，benchmark 数值仍只作手动诊断。

## 后续验收重点

1. 提取稳定性：增加不同措辞和多次固定样本回放，按全量完成率与错误计分，单独验证事实替代、证据和 Key Memory；不能靠增加随机重试把失败抹去。
2. 复杂召回：以 development 集比较查询指令、来源分段、混合检索 / reranker，再用新的未触碰 holdout 验收。当前已查看的 holdout 后续应视为已使用；不能再当盲测。模型查询指令应遵守[官方模型文档](https://huggingface.co/Qwen/Qwen3-Embedding-4B)，本次没有临时调参再重报外部成绩。
3. 性能：分解 embedding 排队、缓存、候选补全与 SQL，评估模型/维度、批处理和 ANN 方案，复测固定吞吐和实际并发；任何近似索引改动必须同时检查召回与用户作用域。
4. 扩大 LongMemEval 至全量并补独立回答评测，再做真实模型 rebuild / activation 验收。小样本高分不能关闭这些任务。
